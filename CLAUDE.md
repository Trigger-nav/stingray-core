# Stingray — Project Context

Stingray (Stingray Marine Technology, stingraymarinetechnology.com) is a **passage & performance optimisation** platform for superyachts: multi-objective optimisation of route, speed, and vessel setup (engine config, trim) against a captain-selectable mix of fuel economy, ETA, comfort, and wear — sold to yacht management companies as an efficiency + IMO/SEEMP compliance tool. Advisory-only by design (no control outputs); the captain always retains authority.

## Non-negotiable design principles

1. **Edge-first:** all planning/inference must run offline on modest ARM hardware; cloud is never in the critical path.
2. **Advisory-only:** no control outputs, ever, in this phase.
3. **Graceful degradation:** every feature must define behaviour at each sensor tier (full integration / NMEA + engine fuel rate / NMEA + manual fuel).
4. **No invented numbers:** every prediction carries a confidence interval; the twin is physics-informed and interpretable (separate calm-water, added-resistance, SFOC, motion components), not a monolithic black box.
5. **Privacy:** yacht position data is owner-sensitive; per-vessel isolation, anonymised aggregates only.

## Phase 0 engineering conventions

- Python 3.11+, `pyproject.toml`, `pytest`, `ruff`; type hints throughout. Port hot paths to Rust later only if profiling demands it.
- Package layout: `core/` (twin, optimiser, weather) as a library with no I/O side effects; `ingest/` for data acquisition; `fit/` for twin parameter fitting (ticket 0.6 — depends on `core/` one-way, same direction `ingest/` does, plus `scipy` for real nonlinear least-squares; its own `fit` extras group, not folded into `ingest`); thin CLIs on top.
- Real geography: GSHHG coastlines (land mask), GEBCO 2024 bathymetry. Real weather: NOAA NOMADS GRIB2 + ECMWF open data, parsed with cfgrib (needs `brew install eccodes`).
- Every optimiser change must keep the regression suite green: known scenario → expected plan-shape assertions (e.g. mistral + comfort-heavy weights ⇒ lee-side routing; ETA window infeasible ⇒ flagged, fastest-first ordering).
- `pytest` (bare) runs the fast suite (~29s) — `RealGeography`-heavy searches are marked `@pytest.mark.slow` and excluded by default (`addopts` in `pyproject.toml`; one test, the fine-resolution navigability sweep, is ~370s alone). Run `pytest -m ""` for the full suite (what CI runs) before trusting an optimiser/geography change.
- Ticket 0.7 (savings-verification methodology) is a written deliverable, not code — do not skip it; the commercial claim depends on it.

## Gotchas

- The demo twin's coefficients are synthetic. Port the *structure*, not the constants; constants become fitted parameters with priors in Phase 1.
- **Bonifacio Strait — resolved, ticket 0.8 (2026-07-08).** The strait is a scattered field of dozens of small real granite islets (Iles Lavezzi). `core/corridors.py`'s hand-drawn `corridor_west()` waypoint segment is feasible under `RealGeography` again as of this ticket — it was infeasible at every speed/engine combination under the old *synthetic placeholder* no-go box `RealGeography` used pre-0.8 (which happened to cover the lateral-offset water the corridor's DP needed around the islets), and ticket 0.8's real, precisely-cited no-go geometry no longer blocks it (verified: ~193nm, clean; see that function's docstring). It's a true fast-path fallback for this passage once more, not something callers must avoid relying on. The open lattice search (`core/lattice.py`) is still the primary/more-thorough search and still backs `core/optimiser._baseline_route` regardless — it *can* thread the strait too, via two independent, both-necessary fixes found empirically (see `docs/plans/ticket-0.8.md`'s "The actual Bonifacio blocker, found empirically" section for the full trace): (1) **adaptive per-stage lattice refinement** (`core/lattice.py`'s `build_lattice(..., geography=...)`) — the strait's genuine, asymmetric (west-worse-than-east) scattered-islet degradation needs finer local resolution than the passage-wide default, refined down to a 0.5nm floor at the worst stages (still short of full navigability there — expected, real chart data will do better than this bench's coarse GEBCO/GSHHG crop); (2) a **side-diversity filter bug fix** (`core/optimiser._side_diversity_filter`) — the old version constrained lane sign identically at *every* stage of the passage, not just the Corsica-spanning "distinguishing region", which was silently forcing the west-side search onto real Sardinian coastline at the destination's final approach — this, not the reef field itself, was the actual hard blocker. Fixing (2) without (1) reintroduced a different failure (a west-side route pushed into the reef field couldn't turn back to the approach fast enough); the turn-rate/lattice-resolution parameter governing that (`core/lattice.LANE_TURN_RATE_NM`) needed re-tuning from a naive index→nm conversion (10nm) to an empirically-confirmed-sufficient 15nm once turn allowance was fixed to be physical-distance-based rather than lane-index-based across a coarse/fine stage boundary (a related bug, see `core/lattice._turn_range`'s docstring). Minimum-depth (`core/legs.py`, `DEPTH_EXEMPT_RADIUS_NM` pilotage exemption near declared endpoints) and no-go/TSS-separation-zone hard constraints (`core/geography.RealGeography`, `data/geography/nogo_western_med.json`/`tss_western_med.json`) are both now wired in. **Still open, deliberately scoped out:** the TSS zone is a real, cited bounding box (Scandola, Iles Lavezzi — marineregions.org MRGIDs 26848/3457) for the no-go zones, but the Bonifacio TSS file itself is an explicitly-labelled **placeholder** (no free, verified source for the real IMO-adopted lane geometry was found this ticket), and it models the separation **zone** as a hard no-go only — directional **lane** compliance (COLREG Rule 10, which side/heading) is not modelled at all. Sourcing the real TSS lane geometry (a chart or IMO routeing-system publication) is the concrete follow-up.
- Time-dependent costs: weather varies over the passage — the search must be over a time-expanded graph, not a static one.
- GRIB conventions vary (0–360 vs −180–180 longitudes; wave direction "from" vs "to"). Normalise at the ingest boundary and test it. **Ticket 0.5 findings (confirmed live against real NOMADS/ECMWF endpoints during scoping, `docs/plans/ticket-0.5.md`):** NOMADS' `filter_gfs_0p25_1hr.pl`/`filter_gfswave.pl` grib-filter endpoints do real server-side bbox subsetting (tiny downloads, hourly GFS wind + WW3 wave through 48h+); ECMWF open data has no server-side subsetting but ships a `.index` byte-offset sidecar per file enabling cheap HTTP Range requests for a single param out of a whole-globe file. ECMWF's `mwd` (wave stream) is confirmed WMO from-convention. **First real run completed 2026-07-07 (eccodes installed, both fetchers run live, `verify_grib_consistency` passed):** WW3's direction convention is **empirically confirmed from-convention** — mean cross-source wave-direction disagreement 16°, Hs agreement within 0.11 m — so `ingest.grib_common.WW3_DIRECTION_IS_TO_CONVENTION` stays `False`. `tests/test_grib_parsing.py`'s cfgrib fixture tests run and pass (variable-name mapping verified). Two residual follow-ups: tighten the permissive `_find_var` matching in `fetch_grib_nomads.py` now that real cfgrib names are known, and note `scipy` is required by the WW3→GFS grid resampling (added to the `ingest` extra after the first run flushed it out).
- **Ticket 0.6 (twin fit/validate tooling) findings, all found empirically while building the acceptance test, not theorised in advance:** (1) power/SFOC identifiability is genuinely degenerate at a single `active_engines` value — `fit/calm_resistance.py`'s docstring has the full argument; the synthetic conditions grid must span multiple engine configs at overlapping speeds, and `FitResult.engine_configs_present`/`.prior_shift_sigma` are the diagnostic. (2) The calm-power steepening term (`steepening_coefficient`/`steepening_exponent`) is poorly identified unless the speed range actually reaches past the hull's steepening onset (~16-17kn for the shipped 45m hull, `hull_speed_froude=0.4`) — a grid stopping at 16kn barely probes it; `fit/synthetic.py`'s `DEFAULT_SPEEDS_KN` now reaches 18kn deliberately. (3) Weight each segment's data residual *proportionally* to its own fuel-rate scale (`fuel_noise_std_fraction`, not a fixed absolute kg/h) — a fixed absolute std silently overweights high-speed/high-fuel-rate segments relative to low-speed ones and was the single biggest source of poor fit quality found during validation (fixed before this landed; see `fit/calm_resistance.py`/`fit/added_resistance.py`). (4) Individual fitted parameters can still be a poor match to ground truth (multiple correlated parameter combinations fit the same data almost equally well) even when the fitted *function's predictions* are accurate — the acceptance test asserts on predictive agreement for exactly this reason, not raw parameter recovery.
- **`optimise()` cost is dominated by uncached weather sampling, not lattice-building — found empirically during ticket B1, correcting an initial wrong assumption.** A cold call against `RealGeography`+real `GriddedWeatherField`+the full default speed grid costs ~19s; `cProfile` showed the true bottleneck is `core/weather.py`'s `GriddedWeatherField.sample()`/`core/gridding.py`'s bilinear interpolation inside `evaluate_leg` (~690k calls across the default grid), which is *not* cacheable like `core/legs.py`'s navigability/depth `lru_cache`s — each call samples weather at a different position *and time* (ETA varies by candidate speed/route, the whole point of the time-expanded search, B2). `core/lattice.py`'s `build_lattice` itself *does* benefit hugely from a warm process (~0.4s cold → ~0.02s warm) but isn't the dominant cost. Concretely: **reusing a warm worker process does not meaningfully speed up a subsequent `optimise()` call** — `api/state.py`'s `_worker_init` originally tried a full `optimise()` warm-up call for exactly this (wrong) reason and was reverted to a cheap weather-data sanity check once profiling corrected the assumption (see that function's docstring for the full trace). Validates the ~8-60s job-duration assumption behind B1's job-shaped API design (contract point 1) — this is real, structural cost, not a missing cache.
- **`STINGRAY_ROLE=cloud\|vessel` (ticket B1, `api/config.py`) is the one flag that makes the identical planner-service codebase serve two deployment targets** — the pilot cloud VM and the yacht's bridge PC (B5's amended MVP shape). `cloud`: runs the existing, unmodified `ingest.fetch_grib_*` on a cron and serves the compact npz via `GET /v1/weather/latest.npz`; sits behind a TLS reverse proxy (Caddy, `deploy/linux/Caddyfile`) since it's public-internet-facing (`docs/pilot/data-agreement-outline.md`'s encryption-in-transit commitment). `vessel`: never imports `ingest.*` at all — instead pulls that npz opportunistically over conditional HTTP (`api/weather_sync.py`), feeding the exact same local-file hot-swap mechanism cron feeds on the cloud side; binds to the ship LAN/localhost only, plain HTTP (`TECHNICAL_ARCHITECTURE.md` §8's "no internet exposure of the edge device" principle applies here too). The cloud/vessel split isn't just a config nicety — it's what keeps `ingest`'s `cfgrib`/system-`eccodes` dependency (this repo's most fragile cross-platform C-library dependency, see the GRIB-conventions gotcha above) entirely out of the Windows/macOS PyInstaller build.
- **Ticket B2 (connecting `prototype/stingray_planner.html` to the real `api/` planner) — three reusable patterns, first hit in this repo's JS, worth carrying into ticket 2.2's real bridge app:** (1) **request-generation-counter stale-response guard** — every async submission (`requestPlan()`'s `_reqGen`, `renderUI()`'s own separate `_drawGen` for the weather-field draw path) increments a monotonic counter before awaiting, then checks it's still current before acting on the result; the minimum mechanism that guarantees UI correctness under overlapping/out-of-order network responses (e.g. rapid slider drags, rapid forecast-scrub) without needing `AbortController`-based cancellation (deliberately not built — the counter alone is sufficient for correctness, actual cancellation is a real but cut optional efficiency gain). (2) **Accepted precision loss in the vessel-state "optimality" panel**: `vstateRows()`'s same-side/overall comparisons now run only over `[...candidates, baseline]` (2-4 points) instead of the old synthetic brain's ~16-candidate internal sweep — a plan can trivially read "100% optimal" if the same-side subset happens to contain only itself. This is a deliberate consequence of *not* touching `core/optimiser.py`'s return shape (would have crossed the bridge-section optimiser feature freeze pending ticket 1.5), not a bug — don't "fix" it without first widening what the job-shaped API returns. (3) **CORS `allow_credentials=False` is deliberate, not an oversight** — Basic Auth travels via the `Authorization` header, not a cookie, so CORS "credentials mode" (which governs cookie semantics) isn't the relevant mechanism; keeps `allow_origins` free to be an explicit list without the `credentials=True`+wildcard-origins incompatibility ever coming up. If a future ticket switches the auth mechanism to cookies/sessions, this needs revisiting together with `allow_credentials`. Full design/rationale: `docs/plans/ticket-B2.md`.
- **B2's real-browser verification pass (2026-07-09, prototype repo commit `27a8c7e`) found two real bugs neither `pytest` nor `ruff` could have caught, both worth remembering for any future JS touching `res.plans`/`res.baseline`:** (1) **`baseline.score` (`score_eur` on the `CandidateModel` mirror) is `NaN` by design — baselines aren't scored, only optimiser candidates are** — any comparison pool built as `[...res.plans, res.baseline]` must filter to `Number.isFinite(c.score)` before feeding it `Math.min`/`.find(c=>c.score===x)`: `NaN` poisons `Math.min`, and `NaN!==NaN` makes `.find()` return `undefined`, which then throws on the next `.v`/`.corr` property read. `vstateRows()`/`renderVessel()` in `stingray_planner.html` both do this filtering now — don't reintroduce an unfiltered `[...plans, baseline]` score-comparison without it. (2) **Classify errors by type before deciding what banner to show** — `requestPlan()`'s catch block was treating *any* thrown error, including a plain JS bug inside `renderUI()` (a `TypeError` from bug (1), as it happened), as a network/connectivity failure and painting "CONNECTION FAILED" over it. Non-`ApiError` exceptions now get their own distinct `ui_bug` banner ("this is a bug, not a connection problem") instead of silently misdirecting debugging effort at the wrong layer (network) — a pattern worth repeating anywhere a catch-all wraps both "the server said no" and "our own code threw."
- **`core.optimiser.optimise()` used to run its isochrone pre-pass (`core.isochrone.reachable_within`, the dominant cost in `optimise()` — see the weather-sampling gotcha above) *twice* whenever `latest_arrival_h` was tighter than `DEFAULT_HORIZON_H` (48h) — found via B2's manual verification, where a constrained real-browser replan exceeded the demo's poll deadline while unconstrained requests didn't.** The second call was for the baseline's own reachable set (`baseline_reachable`, needed because the baseline is a do-nothing reference that mustn't be pruned by the request's own tight window — see `_baseline_route`'s docstring) — a second full Dijkstra pass at the generous default horizon, on top of the first at the request's own (tighter, cheaper) horizon. Profiled against `RealGeography`+real `GriddedWeatherField` (the exact demo passage): ~1.35x total `optimise()` wall time for a representative 13h window, before accounting for any additional worker-pool queueing contention. **Fixed by sharing one Dijkstra pass**: `core/isochrone.py`'s `reachable_within` is now a thin wrapper over two new functions, `arrival_times_within` (returns every reached node's earliest arrival time, not collapsed to a horizon-bounded set) and `arrivals_within_horizon` (a cheap post-filter) — provably correct to share (a Dijkstra run with a larger deadline is a strict superset of a tighter one's exploration; see `arrival_times_within`'s docstring for the full argument), not an approximation. `optimise()` now calls `arrival_times_within` once at `max(horizon_h, DEFAULT_HORIZON_H)` and derives both `reachable` and `baseline_reachable` as filters over that one result. Re-profiled after the fix: constrained and unconstrained now cost the same (one Dijkstra pass either way — confirmed via `_best_feasible_duration_h`'s call count matching exactly between the two cases). `tests/test_optimiser_regression.py`'s `test_latest_arrival_h_shares_one_isochrone_search_not_two` is the regression test (monkeypatches `core.optimiser.arrival_times_within` to assert it's called exactly once). **Also, defense-in-depth in the UI** (`prototype/stingray_planner.html`'s `optimise()`): even with the server-side fix, worker-pool contention under real concurrent interactive use (a burst of superseded-but-still-server-side-running jobs — the client never cancels those, a deliberate B2 scope cut) can still occasionally push latency past a fixed deadline, so hitting the old 90s deadline no longer throws immediately — it's now a *soft* deadline (fires an `onSlow` callback so the UI can say "still computing" instead of giving up) with a 5-minute hard ceiling before actually failing. The point: a client that gives up early doesn't stop the job running server-side — it just stops the client from ever seeing the result it's about to get.
- **`deploy/linux/install.sh` never actually copied `data/` to `/opt/stingray/data` — found during a Hetzner deploy-readiness review, not the macOS trial build, because that trial build happened to run `dist/stingray` from inside the repo checkout (where `data/` already existed in the cwd by coincidence), never through the real `install.sh` → `/opt/stingray` path.** `api/config.py`'s default data paths (vessel spec, geography, seed weather npz) are plain relative strings resolved against the process's working directory (`stingray-planner.service`'s `WorkingDirectory=/opt/stingray`) — `install.sh` only ever copied the binary + wrote `.env`, leaving `data/` an empty `mkdir -p`. **`deploy/pyinstaller.spec`'s `datas=[(repo_root/"data","data")]` does NOT cover this** — PyInstaller onefile mode extracts bundled `datas` to a throwaway `sys._MEIPASS` temp dir at every run, and nothing in `core/`/`api/` checks `sys._MEIPASS` (confirmed: zero hits repo-wide), so that bundled copy is inert dead weight, never read. Fixed by having `install.sh` `cp -r` the real `data/` from the checkout it's already being run from (build requires a full checkout anyway, PyInstaller can't cross-compile) — deliberately not by making `core/` `sys._MEIPASS`-aware, to keep `core/` deployment-agnostic and avoid touching the already-trial-verified PyInstaller spec right before a real deploy. Full reasoning: `docs/plans/deploy-readiness-hetzner.md`.
- **`deploy/.env.example` didn't mention `STINGRAY_CORS_ORIGINS` at all — the single most likely real-deploy failure mode for the cloud role.** A cloud instance can come up fully healthy (`/v1/health` responds fine) while the hosted demo silently never shows a plan, with no server-side error to grep for — a CORS-rejected preflight is answered by the browser itself, never reaching application code. Now documented with the demo's real origin (`https://trigger-nav.github.io`) as the example value and explicit "this is the #1 silent-failure risk" framing.
- **`eccodes` on Ubuntu 24.04 — verified live on the real Hetzner deploy (2026-07-13).** `deploy/README.md`'s Cloud VM runbook's `libeccodes-dev` apt package works as expected: `import cfgrib` and a real GRIB fetch both succeed cleanly, closing the gap ticket 0.5 left open (previously only macOS's `brew install eccodes` had been confirmed live). The documented `pip install eccodes` fallback (vendors a compiled ecCodes via wheel on common Linux platforms) remains untested — not needed since the standard apt route worked first try.
- **`python3 -m api.main` didn't actually work before this fix, despite `deploy/stingray_cli.py`'s own docstring promising it as "the normal, non-packaged dev invocation."** `api/main.py` had no `if __name__ == "__main__":` block — running it that way just imported the module and exited. Fixed by adding one (mirrors `deploy/stingray_cli.py`'s `_run_planner()`: same `app` object, not the `"api.main:app"` string form, host/port from `Settings.from_env()`). Also found live during B2's manual verification: **backgrounded local dev servers (`python3 -m api.main`, `python3 -m http.server` for `prototype/`) are easy to lose track of and leave orphaned across a session, each still holding its port** — symptom is a fresh server mysteriously failing to bind, or requests silently hitting a stale process serving old code. `deploy/README.md`'s new "Local dev server" section has the `lsof -iTCP:<port> -sTCP:LISTEN` / `kill` recipe.
- **`GET /v1/weather/field?h=N` (`api/weather_field.py`, ticket B2 amendment) is a display-only downsample, never the source grid — don't extend it into a general weather-query endpoint.** Built entirely on `core.weather.WeatherField.sample()` (same interpolation the optimiser itself uses, zero new `core/` code), fixed at a small 30×32 grid regardless of the source data's real resolution, with `h` quantized server-side to the nearest whole hour before sampling (`quantize_hour()`) — both because source weather data is hourly-to-3-hourly resolution (serving sub-hour precision would be fake precision) and because it's what makes the ETag cache-friendly across a continuous `#tscrub` scrub gesture (many nearby scrub positions collapse onto one served hour → cheap `304`s). Exists specifically to feed `drawWx()`'s chart heatmap/wind layer — the third, initially-missed `SCENARIOS[scId]` client-side call site from B2's original research pass (caught in review before implementation, not after).
- **`api/jobs.py`'s queue-depth cap (`max_queue_depth`, ticket B2 amendment) must refresh every `JobRecord` before counting in-flight jobs, or it overcounts.** `JobRecord.status`'s property only reflects a completed `Future` once `_refresh()` has actually run (it's what sets `finished_at`) — a naive count of records with `status in ("queued","running")` over unrefreshed records misreads a completed-but-never-polled job as still queued. `JobStore.submit()` refreshes all records under its lock before counting; `tests/test_api_jobs.py`'s `test_submit_refreshes_before_counting_so_a_completed_unpolled_job_does_not_overcount` is the regression test. This cap (protects the bounded `ProcessPoolExecutor` from an unbounded submission backlog, `429`+`Retry-After`) is a distinct bound from the pre-existing TTL/`job_max_size` eviction sweep, which bounds total *stored* record count over time, not concurrent in-flight work.
- **Ticket B1's cross-platform packaging (PyInstaller, `deploy/pyinstaller.spec`) needed two empirically-found fixes, neither guessable from the spec file alone — found via a real trial build (macOS/arm64) this ticket, not assumed to work:** (1) `nmea2000`'s `decoder.py`/`encoder.py` load `.decoder_formats`/`.encoder_formats` via `importlib.import_module(...)`, not a static `import` — PyInstaller's analysis can't see that, the build succeeds silently, and it only fails at *runtime* (`ModuleNotFoundError`) the first time a decode/encode is attempted; both are now explicit `hiddenimports`. (2) `ProcessPoolExecutor` workers have no separate `python.exe` to re-exec inside a frozen binary, so they re-launch *the same frozen executable* — without `multiprocessing.freeze_support()` as the very first call in `deploy/stingray_cli.py`'s `if __name__ == "__main__":` block (before any CLI-argument dispatch), each worker re-invocation hits the "usage: stingray {planner|capture}" branch and exits immediately, and the whole pool comes up `BrokenProcessPool`. Also found: `uvicorn.run("api.main:app", ...)` (the string form) is itself a dynamic import PyInstaller can't trace and fails at runtime inside the frozen binary even though it works fine in normal dev use — pass the `app` object directly instead. Within one left-to-right sweep, per-waypoint accept/reject decisions are local (O(n) `evaluate_leg` calls); the actual accept/reject authority for the *whole pass* is a genuine end-to-end re-evaluation of the resulting track (`_evaluate_whole_track`), discarding the whole pass if the true total cost came out worse — deliberately not a per-merge whole-remaining-track recheck (correctness-equivalent but O(n²)). Deliberately has zero dependency on `core.optimiser` (avoids a circular import — `optimise()` is this module's only caller); `leg_targets`/`alteration_list` are rebuilt by the caller via the existing, unmodified `_build_leg_targets`/`_build_alteration_list`. `Candidate.side` (route signature) is captured from the *original*, pre-distillation track and deliberately never touched by distillation — the one field this module doesn't recompute. **Unlike R1/C1, S1 explicitly cannot claim "zero behaviour change"** — its entire purpose is to change the returned track (fewer waypoints, equal-or-better score). The freeze defence instead: the search machinery itself (lattice resolution, turn rate, side-diversity filter, hard constraints, cost model) is completely untouched; plan-*shape* assertions (side labels, window-feasibility booleans, diagnostic codes, hard-constraint pruning, endpoint identity) hold unmodified by design; plan-*numeric* assertions were individually re-verified, not blanket-preserved — `test_pure_schedule_weights_converge_to_isochrone_time_optimal` (the one test flagged in advance as worth a close look, a 5%-tolerance duration-vs-oracle comparison) passed unmodified. **One real, unexpected regression was found and fixed during implementation — not the flagged test, a different one.** `optimise()`'s pre-existing top-3 `picks` selection (unrelated to S1's own design, untouched machinery) is a greedy, cost-order-dependent algorithm — take the cheapest candidate, then walk the cost-sorted pool taking up to 2 more that are "diverse" (different `side`, or ≥2kn speed difference), **stopping as soon as 3 are found** — it never actually guaranteed every reachable side would be represented; it happened to work out that way before. S1's real, legitimate per-side cost improvements are uneven (the Bonifacio W corridor, which winds around the Iles Lavezzi islets, had more removable kinks than E) — this reordered the cost-sorted pool enough that a slower W candidate (11kn) dropped below the E candidate's cost and got greedily grabbed first, silently excluding E entirely from the final `picks` even though the full candidate pool still contained an improved-cost E-side route (`test_bonifacio_strait_transit_is_reachable_at_current_lattice_resolution`, ticket 0.8's own regression test, caught this). Given the choice between loosening the test or fixing the algorithm, the user chose to fix the algorithm — a real, pre-existing product gap S1's own improvements happened to expose, not a test-fixture mismatch. Fixed with two changes to `optimise()`'s `picks` construction: (1) after taking the single cheapest candidate, guarantee at least one candidate per distinct reachable `side` present in the pool (each side's own cheapest representative) before the original greedy cost-order fill claims any remaining slots; (2) **re-sort `picks` at the end** by the same key `pool` itself was sorted with (`duration_h` when `missed_window`, else `score_eur`) — required because (1) can insert a side's representative out of `pool`'s own order, which broke `test_impossible_eta_window_flags_and_orders_fastest_first`'s fastest-first-ordering assertion before this second fix was added. Both tests pass after both changes; a full `pytest -m ""` run confirmed nothing else regressed. **Real Med+UK acceptance run** (`docs/plans/ticket-S1.md`): 50-81% fewer waypoints per matched candidate (Med Antibes↔Porto Cervo, UK Plymouth↔Falmouth, real geography + real weather), no candidate ever scored worse, `side`/`corridor_name` identical before/after for every matched candidate. `distill_track` itself directly instrumented (not inferred from a noisy whole-`optimise()`-call wall-clock difference, which is dominated by the search's own much larger cost per the B1 profiling gotcha): ~1.3-1.5% of total `optimise()` wall time — matching the plan's own B1-derived ≤1% estimate. `PlanRequest.distill: bool = True` (mirrored exactly by `api/schemas.py`'s `PlanRequestIn.distill`, threaded through `api/convert.py`/`api/state.py`'s `PlanJobPayload`) is default-on so the hosted demo and every existing caller see the improvement with zero client changes — a real `POST /v1/plans` with `distill=false` round-trips to a genuinely undistilled result, verified against the default Antibes↔Porto Cervo passage specifically (the module's usual short-route test fixture already collapses to a minimal 3-waypoint track regardless of `distill`, so it can't discriminate on/off — found while writing the round-trip test, not assumed).
